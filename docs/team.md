# Team

Wir sind fünf. Jede Person hat eine **Rolle**: Sie ist für einen Bereich die Ansprechperson und behält ihn im Blick.
Rollen sind Verantwortung, keine Grenzen. Alle programmieren, alle reviewen, alle dürfen überall mitarbeiten.

## Wer macht was

Erste Übung für den Git-Ablauf (Issue #2): Trag dich über einen eigenen Branch und Pull Request in deiner Zeile ein.

## Die Rollen

### Projektleitung & Product Owner
- Pflegt das Board: Prioritäten, Meilensteine, welche Issues in den nächsten Sprint kommen
- Hält das Lastenheft und `docs/entscheidungen.md` aktuell
- Leitet das Donnerstagstreffen
- Verwaltet Repo und Webspace: Einladungen, Einstellungen, Zugangsdaten

### Git- & Prozess-Coach
- Erste Hilfe bei Git und GitKraken (Konflikte, „Ich hab mich verklickt“)
- Achtet auf den Ablauf: Branch pro Issue, Pull Requests, Reviews innerhalb von zwei Tagen
- Erinnert an offene Reviews und hängende Karten auf dem Board
- Moderiert im Treffen den Rückblick: Was lief gut, was ändern wir?

### Spiel (Godot & Oberfläche)
- Behält die Struktur in `game/` im Blick: Bildschirme, Komponenten, Autoloads
- Achtet darauf, dass nicht zwei Leute an derselben Szene arbeiten
- Reviewt Pull Requests, die das Spiel betreffen
- Kümmert sich um den Web-Export

### Server (PHP, API & Betrieb)
- Behält `server/` und `docs/api.md` im Blick – die Schnittstelle zwischen Spiel und Server
- Achtet auf Tests und darauf, dass das Wort nie bei den Ratenden landet
- Betreut CI und Deployment zusammen mit der Projektleitung
- Achtet darauf, dass keine Zugangsdaten ins Repo kommen

### Design (Grafik & UX)
- Entwürfe in Figma, abgelegt in `docs/design/`
- Avatare, Hangman-Grafik, einheitlicher Look
- Prüft, ob die Bedienung ohne Erklärung verständlich ist

## Reihum

- **Protokoll** im Donnerstagstreffen: jede Woche eine andere Person, Datei in `docs/meetings/`.
